1. File Descriptor Basics

A file descriptor (FD) is an index that the kernel uses to locate a struct file in kernel memory. The struct file is a generic kernel object used for files, sockets, pipes, and more.

Key Concept: System calls cause CPU mode switches so the kernel can operate on these structures.

The struct file abstraction unifies:

  • Regular files
  • Directories
  • Pipes
  • Sockets
  • Devices
Process FD Table +---------------------------+ | FD 3 → struct file A |----+ | FD 4 → struct file B |----|-+ +---------------------------+ | | v v (in kernel space)

2. The struct file

The struct file resides in kernel memory and is invisible to user space.

Simplified Structure

// Simplified representation struct file { mode_t f_mode; // read/write/append/truncate flags loff_t f_pos; // current offset in file const struct file_operations *f_op; // function pointers for read/write struct path f_path; // contains pointer to inode + mount point atomic_t f_count; // reference count void *private_data; // used by drivers/sockets };

Linux 5.10+ Complete Definition

struct file { union { struct llist_node fu_llist; struct rcu_head fu_rcuhead; } f_u; struct path f_path; // dentry + mountpoint struct inode *f_inode; // cached value const struct file_operations *f_op; spinlock_t f_lock; atomic_long_t f_count; // reference count unsigned int f_flags; // O_RDONLY, O_WRONLY, etc. fmode_t f_mode; struct mutex f_pos_lock; loff_t f_pos; // current file position struct fown_struct f_owner; struct cred *f_cred; // credentials (UID, GID) struct file_ra_state f_ra; // readahead state u64 f_version; void *f_security; // SELinux, etc. void *private_data; // *** MOST IMPORTANT *** struct address_space *f_mapping; // memory mapping info } __randomize_layout;
CRITICAL FIELD: private_data
This field is used for sockets (struct socket), pipes, character devices, block devices, and special filesystem state.

3. The struct inode

The inode represents the file's metadata and is shared across multiple file descriptors pointing to the same file.

struct inode { umode_t i_mode; // permissions + file type unsigned long i_ino; // inode number const struct inode_operations *i_op; struct super_block *i_sb; // filesystem loff_t i_size; // file size struct timespec64 i_atime; // access time struct timespec64 i_mtime; // modify time struct timespec64 i_ctime; // metadata change time struct address_space *i_mapping; // page cache atomic_t i_count; // reference count };

Sharing Inodes

PROCESS FD TABLE +---------------------------+ | FD 3 → struct file A |----+ | FD 4 → struct file B |----|-+ +---------------------------+ | | v v struct file A struct file B +-------------------+ +-----------------+ | f_mode | | f_mode | | f_pos (offset A) | | f_pos (offset B)| | f_path ---------- |--+ | +-------------------+ | | v v struct inode (SHARED) +----------------------------+ | i_mode (permissions) | | i_ino (inode number) | | i_size (file size) | | i_atime, i_mtime, i_ctime | | i_mapping (page cache) | +----------------------------+
Note: Multiple file descriptors can point to different struct file instances (each with their own position), but they all share the same struct inode for metadata.

4. Socket Architecture

For sockets, the kernel uses a layered structure connecting the file descriptor to the actual network protocol implementation.

PROCESS ------------------------------------------------ file descriptor table fd = 3 ----------------+ | KERNEL | ------------------------------------------------ struct file <------------+ → f_ops → flags → private_data | v struct socket → type → ops → sk (pointer to struct sock) | v struct sock (TCP) → state → local IP/port → remote IP/port → send buffer → receive buffer → accept queue → pending queue → protocol info

struct socket

struct socket { socket_state state; // SS_CONNECTED, SS_UNCONNECTED, etc. short type; // SOCK_STREAM, SOCK_DGRAM, etc. unsigned long flags; struct socket_wq *wq; // wait queue for blocking operations struct file *file; // back-pointer to struct file struct sock *sk; // *** MOST IMPORTANT *** const struct proto_ops *ops; // read/write/send/recv/bind/listen };
The sk field points to the actual protocol instance (struct sock), which contains all the TCP/UDP state information.

5. TCP Connection Establishment

Port Binding

The kernel maintains a port table (per protocol) where each (IP, PORT) pair can have at most ONE listener.

┌──────────────────────────────┐ │ Kernel │ │ (TCP/UDP stack) │ └──────────────────────────────┘ │ │ bind(IP, PORT) ▼ ┌──────────────────┐ │ Port Table │ │ (per protocol) │ └──────────────────┘ Example entries: ┌────────────────────────────────────────┐ │ (0.0.0.0, 22) → socket_fd 4 (sshd) │ │ (127.0.0.1,5432) → socket_fd 8 (postgres) │ │ (0.0.0.0, 80) → socket_fd 5 (nginx)│ └────────────────────────────────────────┘

Three-Way Handshake

CLIENT SERVER ────────────────────────────────────────────── local_ip = 192.168.1.20 local_ip = 192.168.1.10 local_port = 50321 local_port = 8080 remote_ip = 192.168.1.10 remote_ip = 192.168.1.20 remote_port = 8080 remote_port = 50321 ────────────────────────────────────────────── 1. SYN (seq = x) Client --------------------------------> Server 2. SYN + ACK (seq = y, ack = x+1) Client <-------------------------------- Server 3. ACK (ack = y+1) Client --------------------------------> Server

6. SYN Queue & Accept Queue

The kernel allocates memory for struct socket BEFORE accept() is called. When the client sends the final ACK, accept() simply adds a new entry to the process FD table and returns its index.
┌─────────────────────────────────────────┐ │ LISTENING SOCKET │ │ (created by socket + bind + listen) │ └─────────────────────────────────────────┘ │ │ Incoming SYN ▼ ┌─────────────────────────────────────┐ │ SYN QUEUE (request_sock) │ │ Half-open connections (SYN_RECV) │ └─────────────────────────────────────┘ │ │ Client sends final ACK ▼ KERNEL allocates full TCP socket -------------------------------- - TCP state - seq/ack numbers - buffers - timers - MSS/window - client IP/port │ ▼ ┌───────────────────────────────────────┐ │ ACCEPT QUEUE (ESTABLISHED) │ │ Fully created connections waiting │ │ for accept() │ └───────────────────────────────────────┘ │ │ Application calls accept() ▼ ┌─────────────────────────────────────────┐ │ PROCESS FILE DESCRIPTOR TABLE │ │ │ │ fd=5 ──────> struct file ──────> socket│ │ (created NOW) │ └─────────────────────────────────────────┘

The listen() Function

What listen() does:
  • Activates the socket for accepting connections
  • Switches TCP state to LISTEN
  • Creates two queues (SYN queue + Accept queue)
  • Sets backlog for pending accepted connections
  • It does NOT accept anything—it only prepares the kernel to do so
Default backlog in Linux: /proc/sys/net/core/somaxconn = 4096
If you configure listen() with a value > 4096, the kernel will cap it at 4096.

7. DDoS Protection Mechanism

What is DDoS?
DDoS (Distributed Denial of Service) is a method used to crash servers by sending millions of SYN packets from attackers using fake IP addresses. The server sends SYN+ACK and waits for the final ACK, which never arrives. This fills the queue and prevents legitimate clients from connecting.

How the SYN Queue Protects Against DDoS

The kernel allocates a lightweight struct in the SYN queue until it receives the final ACK. Upon receiving the ACK, it:

  1. Copies the connection to the accept queue
  2. Removes it from the SYN queue
  3. Waits for accept() to create an FD table entry
SYN QUEUE Client SYN → SYN Queue → (SYN+ACK) → wait for final ACK After handshake finishes → put in accept queue → wait for accept() Connections here are ready, but the app does not see them until accept()

8. Network Stack Processing

High-Level Flow

┌───────────────┐ │ NIC Hardware │ │(Ethernet/WiFi)│ └───────┬───────┘ │ Packet arrives ▼ ┌───────────────┐ │ DMA Engine │ │ Copies packet │ │ to RX buffers │ └───────┬───────┘ │ DMA complete interrupt ▼ ┌───────────────┐ │ CPU / IDT │ │ jumps to IRQ │ └───────┬───────┘ │ ▼ ┌──────────────────────────────┐ │ NIC IRQ Handler (HardIRQ) │ │ Minimal work: │ │ - acknowledge interrupt │ │ - check descriptors │ │ - schedule NET_RX softirq │ └─────────────┬────────────────┘ │ ▼ ┌──────────────────────────────┐ │ SoftIRQ: net_rx_action │ │ Deferred work: │ │ - convert DMA → sk_buff │ │ - Ethernet → IP → TCP/UDP │ │ - socket receive queue │ │ - wake epoll/poll/select │ └─────────────┬────────────────┘ │ ▼ ┌───────────────┐ │ epoll_wait() │ │ (user process)│ └───────┬───────┘ │ returns EPOLLIN event ▼ ┌───────────────┐ │ User process │ │ reads packet │ └───────────────┘

Key Points

Component Description
HardIRQ Runs immediately in kernel mode. Minimal work to avoid blocking other interrupts.
SoftIRQ Runs later, still in kernel context. Handles the network stack and socket queue.
epoll_wait() Sleeps in user space. Woken only when the kernel adds data to the socket receive queue.
DMA Already copied the packet before any interrupt handler runs.
Protection: The NIC only knows about DMA buffers—it has no socket knowledge. Data is never executed due to NX (No-eXecute) protection.

9. DMA Ring Buffers

The NIC uses a ring buffer of descriptors to manage incoming packets efficiently.

┌───────────────────────────────┐ │ NIC RX Descriptor Ring (RAM) │ └───────────────────────────────┘ Descriptor 0 Descriptor 1 Descriptor 2 ... ┌─────────┐ ┌─────────┐ ┌─────────┐ │ addr │ │ addr │ │ addr │ │0x12AB0 │ │0x12AB8 │ │0x12AC0 │ │ length │ │ length │ │ length │ │ status │ │ status │ │ status │ └────┬────┘ └────┬────┘ └────┬────┘ │ │ │ ▼ ▼ ▼ ┌────────────┐ ┌────────────┐ ┌────────────┐ │DMA Buffer │ │DMA Buffer │ │DMA Buffer │ │ (Kernel) │ │ (Kernel) │ │ (Kernel) │ │0x12AB0000 │ │0x12AB0800 │ │0x12AB1000 │ └────────────┘ └────────────┘ └────────────┘ │ │ │ └─────────────┴─────────────┘ ▲ │ DMA copies incoming packet here │ (physical memory, NX-protected) │ ┌───────────────┐ │ NIC Hardware │ └───────────────┘
Important: DMA buffers are in physical memory with NX protection, ensuring that data cannot be executed as code.

Summary

This guide covered the essential components of the Linux kernel's approach to file descriptors, sockets, and network packet processing:

  • File descriptors are indices to struct file objects in kernel space
  • struct file provides a unified abstraction for files, sockets, pipes, and devices
  • Sockets use a layered structure: FD → struct file → struct socket → struct sock
  • TCP connections use SYN and accept queues to manage handshakes
  • DDoS protection is achieved through lightweight SYN queue entries
  • Network processing uses HardIRQ → SoftIRQ → epoll architecture
  • DMA ring buffers enable efficient zero-copy packet reception
